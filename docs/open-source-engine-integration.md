# خارطة دمج المحركات مفتوحة المصدر

## الهدف

تطوير منصة الباترون الحالية إلى نظام CAD بارامتري مترابط، مع الحفاظ على واجهة React/TypeScript وThree.js الحالية، وعدم استبدال محرك ناجح قبل إثبات البديل باختبارات قابلة للتكرار.

المسار المستهدف:

قياسات موثقة ← قواعد بلوكات وراحة ← محرك توليد باترون ← قطع وخطوط خياطة ثنائية الأبعاد ← تحقق هندسي وإنتاجي ← جسم ثلاثي الأبعاد موحد ← محاكاة ملابس مستقلة ← تصدير.

هذا المستند يحدد حدود التكامل. لا يعني أن المستودعات الخارجية قد تم تثبيتها أو تشغيلها أو دمجها بعد.

## 1. توزيع الأدوار

| المشروع | الدور المقترح | ما لا ينبغي افتراضه |
|---|---|---|
| المحرك الحالي في TypeScript | CAD تفاعلي في المتصفح، التحرير، الأبعاد، الطبقات، المعاينة السريعة | لا يُفترض أنه يغطي وحده كل قواعد التفصيل أو المحاكاة |
| PyGarment / GarmentCode | محرك مرجعي/خلفي لتوليد مكونات وقطع خياطة بارامترية من برامج Python | ليس بديلاً فورياً لواجهة CAD الحالية، ولا يعني تثبيت pygarment وحده توفر محاكي Warp |
| GarmentCodeData | أمثلة وبيانات مرجعية تربط الملابس ثلاثية الأبعاد بباترونات الخياطة | شروط بيانات المجموعة ليست تلقائياً هي رخصة كود PyGarment |
| SOMA-X | طبقة موحدة اختيارية لهوية الجسم والهيكل العظمي والطوبولوجيا | ليس محرك باترون ولا محاكي قماش ولا أداة قياس شريطية جاهزة |
| Anny | مصدر محتمل لهندسة جسم بارامترية بنطاق عمري واسع | لا يحول معاملات phenotype مباشرة إلى محيطات سم دون fitting ومعايرة |
| GarmentMeasurements | مصدر/مرجع لنماذج قياسات الجسم وPCA | مستودعه مرخص GPL-3.0؛ يجب مراجعة شروط الكود والبيانات قبل إعادة التوزيع أو الدمج |
| Seamly2D / Valentina | مرجع سلوكي وهندسي لعمليات CAD والتصدير | لا تنسخ الشيفرة أو الصيغ دون مراجعة الرخصة والتبعيات |
| Three.js | عرض القطع والأجسام والنتائج داخل الموقع | العرض الهندسي لا يساوي محاكاة قماش فيزيائية |

## 2. ما الذي تحققنا منه في المصادر

### GarmentCode

المستودع الرسمي يصف PyGarment كمكتبة أساسية لأنواع مثل Edge وPanel وComponent وInterface ومساعدات إنشاء حواف وعمليات هندسية. يحتوي أمثلة برامج ملابس، ملفات مواصفات JSON/YAML، إعدادات أجسام، وواجهة configurator.

تعليمات التثبيت تذكر Python 3.9 في إعداد المستودع، وقيوداً/تبعيات هندسية متعددة، وتوضح أن محاكي NVIDIA Warp المستخدم في مسار المحاكاة نسخة منفصلة تتطلب إعداداً يدوياً. لذلك نعتمد أولاً على مكتبة التوليد ونختبر محاكاة Warp كمسار منفصل.

المراجع:
- https://github.com/maria-korosteleva/GarmentCode
- https://github.com/maria-korosteleva/GarmentCode/blob/main/docs/Installation.md
- https://github.com/maria-korosteleva/GarmentCode/tree/main/assets/garment_programs

### SOMA-X

المستودع والوثائق الحالية يذكران backends اختيارية تشمل MHR وSOMA وAnny وعائلة SMPL وGarmentMeasurements. كما يذكران SOMALayer للجسم الكامل وSOMAHandLayer لليدين، وتوحيد الطوبولوجيا والهيكل العظمي.

الوحدات الأصلية الموثقة في SOMA هي السنتيمتر، المحور الرأسي +Y، والأمام +Z. يدعم SOMA-X ملفات أصول تُحمّل عند الاستخدام، وبعض backends تحتاج إضافات أو ملفات نماذج خارجية. ملفات SMPL/SMPL-X/MANO المرخصة لا يعاد توزيعها مع المشروع. يجب اختبار مسار Anny وملفات الأصول فعلياً قبل اعتماده.

المراجع:
- https://github.com/NVlabs/SOMA-X
- https://nvlabs.github.io/SOMA-X/stable/
- https://github.com/NVlabs/SOMA-X/blob/main/docs/installation.md
- https://github.com/NVlabs/SOMA-X/blob/main/docs/data_assets.md

### قياسات الجسم

واجهة المنصة الحالية تحفظ ملف القياسات بوحدة cm، ومحرك CAD الحالي يعرّف إحداثيات القطع وقيم الأطوال بوحدة cm. يجب عدم تغيير هذه العقود في تكامل أولي. أي محول خارجي مسؤول عن تحويل الوحدات صراحة وتسجيلها في بيانات التصدير.

مستودع GarmentMeasurements يظهر برخصة GPL-3.0 في بيانات GitHub. لا ننسخ شيفرته أو نعيد توزيع أصوله ضمن المنصة قبل مراجعة الرخصة وشروط كل ملف بيانات. ترخيص SOMA-X الأساسي Apache-2.0 لا يلغي تراخيص الأطراف الثالثة.

المراجع:
- https://github.com/mbotsch/GarmentMeasurements
- https://github.com/NVlabs/SOMA-X/blob/main/docs/installation.md

## 3. بنية التكامل المقترحة

### أ. الواجهة الأمامية

تبقى React/TypeScript مسؤولة عن:
- إدخال القياسات والتحقق منها وإظهار مصدر كل قيمة.
- اختيار نوع القطعة والبلوك وقواعد التفصيل والراحة.
- تحرير النقاط والخطوط والمنحنيات والقصات والبنس والبدلات.
- عرض طبقات خط الخياطة وخط القص وعلامات التطابق واتجاه النسيج.
- عرض نتيجة المحرك الخارجي ومقارنة الإصدارات.
- إظهار تقارير التحقق وأخطاء التوافق قبل التصدير.

### ب. عقد بيانات محايد

لا تربط الواجهة مباشرةً بكائنات PyGarment أو SOMA. استخدم عقد JSON داخلياً ذا إصدار ثابت، ثم محولات منفصلة لكل محرك.

العقد الأولي المقترح:

- `schemaVersion`: إصدار العقد.
- `units`: وحدة الأطوال المعلنة، وتكون `cm` في التكامل الأول.
- `measurementProfile`: القيم، مصدرها، وتاريخ/إصدار الملف.
- `easeProfile`: راحة مستقلة حسب المنطقة، لا تدمج مع قياس الجسم.
- `patternPieces[]`: معرف القطعة واسمها وخطوطها وعناصرها.
- `sewingEdges[]`: حواف الخياطة وأنواعها ومعرفات المطابقة.
- `cuttingEdges[]`: خطوط القص بعد تطبيق بدل الخياطة.
- `notches[]`, `grainlines[]`, `darts[]`.
- `validation[]`: نتائج الفحوص والتحذيرات ومصدر القاعدة.
- `provenance`: اسم المحرك وإصداره ونسخة القواعد ومدخلات التوليد.

يجب حفظ خط الخياطة الأصلي منفصلاً عن خط القص. ولا تُعامل سماحة الخياطة كراحة للملبس.

### ج. خدمات Python

عند إثبات الحاجة، تشغّل خدمة Python مستقلة خارج GitHub Pages:
- `POST /api/v1/patterns/generate` لتوليد القطع.
- `POST /api/v1/bodies/fit` لملاءمة نموذج جسم بعد تعريف خوارزمية قياس واضحة.
- `GET /api/v1/engines` لإظهار المحركات والإصدارات والقدرات المتاحة.
- `GET /health` لفحص الخدمة.

كل طلب يحمل `schemaVersion` ومعرف مهمة. كل استجابة تحمل حالة التنفيذ، سجل التحذيرات، إصدار المحرك، والملفات الناتجة. لا يُقبل تنفيذ أو تصدير صامت عند وجود أخطاء هندسية.

هذه واجهات مقترحة وليست endpoints منفذة حالياً. لا توضع مفاتيح أو ملفات نماذج مرخصة داخل مستودع الواجهة أو ملفات GitHub Pages.

### د. العرض الثلاثي الأبعاد

يظل Three.js مسؤولاً عن العرض والتفاعل. تُنقل الأجسام إلى العارض عبر GLB/glTF، وتُنقل قطع الباترون عبر عقد القطع المحايد أو SVG/DXF عند الحاجة. لا نفترض أن GLB وحده يحفظ كل معلومات الخياطة أو قواعد الباترون؛ لذلك يبقى ملف JSON المصاحب هو المصدر الدقيق للبيانات الهندسية.

SOMA-X يوفّر تمثيل الجسم والهيكل العظمي، بينما محاكاة الملابس مسار منفصل يحتاج محرك قماش واختبارات احتكاك/انحناء/تصادم.

## 4. خطة التنفيذ وبوابات القبول

### المرحلة 0 — توثيق العقد والقياس

- توحيد أسماء القياسات وتعريف نقاط القياس ووحدات cm.
- توثيق الفرق بين قياس الجسم والراحة وبدل الخياطة.
- إضافة مصدر القياس ومستوى الثقة والتاريخ.
- تعريف عقد Pattern JSON بإصدار واختبارات schema.
- الحفاظ على التوافق مع المشاريع المحفوظة القديمة.

**القبول:** ملفات القياسات الحالية تُقرأ دون تغيير، وتنجح اختبارات التحويل والتوافق.

### المرحلة 1 — تجربة PyGarment معزولة

- إنشاء بيئة Python منفصلة وعدم إضافة اعتماد PyGarment إلى حزمة المتصفح.
- اختيار مثال بسيط من برامج التنورة/الجذع upstream.
- تشغيله وتسجيل الإصدارات والتبعيات والوقت.
- استخراج القطع والحواف إلى العقد المحايد.
- مقارنة هندسة الناتج بمرجع متوقع، وفحص وحدات القياس واتجاه القطع.
- اختبار تعديل معامل واحد وإثبات تغير متوقع ومحدود في الناتج.

**القبول:** توليد متكرر، قطع صالحة، حواف خياطة معرّفة، وتحويل ذهاب/إياب دون فقد بيانات أساسية.

### المرحلة 2 — محول CAD ثنائي الأبعاد

- بناء محول PyGarment إلى Pattern JSON.
- ربطه بعارض 2D الحالي دون جعل PyGarment مسؤولاً عن التفاعل.
- دعم تحرير الناتج وإعادة التوليد مع تمييز التعديلات اليدوية.
- فحص إغلاق الحدود، التقاطعات الذاتية، أطوال الدرزات المتطابقة، البنس، علامات التطابق واتجاه النسيج.

**القبول:** قطعة تنورة وقطعة جذع على الأقل، قابلة للتحرير والتصدير، مع اختبارات هندسية مستقلة.

### المرحلة 3 — الجسم البشري الموحد

- إكمال اختبار Anny الحالي كمولد جسم مستقل.
- اختبار SOMA-X backend الخاص بـ Anny، ثم مقارنة المخرجات قبل/بعد التحويل.
- التحقق من عدد الرؤوس، اتجاه المحاور، الهيكل العظمي، المقياس، ومواضع المعالم.
- لا يبدأ fitting للقياسات إلا بعد تحديد خوارزمية استخراج محيطات المقاطع والمعالم وخطأ القياس.

**القبول:** ملفات جسم قابلة لإعادة الإنتاج مع تقرير وحدات ومعالم وأخطاء؛ ولا يُدّعى أن الجسم مطابق لقياسات المستخدم دون قياس رقمي ناجح.

### المرحلة 4 — المحاكاة والملاءمة

- تقييم محاكي GarmentCode Warp كخيار منفصل، ومقارنته بخيارات أخرى قبل الالتزام.
- تمرير القطع وخطوط الخياطة إلى المحاكي مع خصائص خامة موثقة.
- فحص التصادم والشد والارتخاء ومناطق الضغط.
- مقارنة المحاكاة بعينة فعلية أو مرجع قياسي؛ المحاكاة وحدها ليست إثبات ملاءمة.

**القبول:** سيناريوهات اختبار قابلة للتكرار، مع تقرير أخطاء وقيود المحاكاة.

### المرحلة 5 — الإنتاج والتصدير

- فصل خطوط الخياطة والقص والبدلات والعلامات.
- اختبار SVG وDXF على أدوات خارجية مستقلة.
- التحقق من مقياس الطباعة 1:1، الأبعاد، تجميع القطع، النسيج، وعدد القطع.
- إضافة حزمة إنتاج تتضمن الباترون والقياسات والمواد والتقارير وإصدارات المحركات.

**القبول:** ملف يعاد فتحه في برنامج CAD خارجي مع أبعاد صحيحة، دون فقد الحواف أو علامات التطابق.

## 5. الرخص والتوزيع

- PyGarment/GarmentCode: بيانات المستودع تشير إلى MIT لكود المستودع؛ راجع ملفات الرخصة لكل مكوّن وتبعية.
- GarmentCodeData: مجموعة البيانات لها صفحة/إصدار وشروط منفصلة؛ لا تفترض أن ترخيص الكود يغطي كل ملفات البيانات.
- SOMA-X: Apache-2.0 للمشروع الأساسي، مع بقاء شروط النماذج والاعتمادات الاختيارية مستقلة.
- Anny: راجع رخصة الإصدار والأصول المستخدمة تحديداً، ولا تستخدم أصول SMPL-X غير التجارية في منتج تجاري دون ترخيص مناسب.
- GarmentMeasurements: مستودع GitHub يعلن GPL-3.0؛ راجع أثر ذلك على أي نسخ أو تعديل أو توزيع، وراجع شروط ملفات PCA/البيانات.
- Seamly2D وValentina: افحص رخصة كل مستودع وإضافاته قبل نسخ الشيفرة أو إعادة استخدامها.

يجب أن تتضمن كل نسخة منشورة ملف THIRD_PARTY_NOTICES يوضح المكونات والإصدارات والرخص والمصادر.

## 6. ما لن نفعله

- لن نستبدل محرك CAD الحالي دفعة واحدة.
- لن نحمّل PyTorch أو Python داخل المتصفح.
- لن نعتبر نموذج الجسم محاكاة ملابس.
- لن نساوي بين phenotype values وقياسات السنتيمتر.
- لن نخلط الراحة مع بدل الخياطة.
- لن ندمج كود GPL أو أصولاً ذات ترخيص خاص دون مراجعة.
- لن نعلن نجاح الملاءمة أو دقة الإنتاج قبل اختبارات قياس وعينات فعلية.

## 7. الحالة الحالية

- محرك CAD TypeScript والعارض Three.js موجودان في المنصة.
- ملفات القياسات الحالية تستخدم cm.
- يوجد PR منفصل لتجربة Anny وإدخال GLB، وهو مسودة ولم يثبت بعد تشغيل Anny فعلياً.
- لا يوجد بعد محول PyGarment، أو خدمة Python منشورة، أو fitting معاير، أو محاكاة قماش متكاملة.
- هذا المستند هو مواصفة معمارية وخطة قبول؛ تنفيذ كل مرحلة يحتاج PR واختبارات مستقلة.
